# Credential retirement: authority, ownership, and safe schema evolution

Keycloak is now the only system that verifies passwords. PocketLedger resolves a provider identity to its own account GUID, then protects that identity with an opaque cookie and a PostgreSQL ticket. A credential authority proves who signed in; an owner ID determines whose expenses can be read. Removing the former authority must not transfer ownership. See [ADR 0020](../decisions/0020-keycloak-credential-retirement.md).

## What changed and why

The register/login slices, password/token ports and services, JWT settings/validation, and Aspire signing-key injection are removed. `UserAccount.Provision` is the only new-account factory and requires `ExternalIdentity`. The repository no longer offers email lookup. Exact issuer/opaque subject uniqueness still handles concurrent first access by reading the winning row after an insert conflict.

Cookies are the default authentication path, including requests without the historical selection header. Sending that header does not choose an identity. Bearer material alone cannot authorize a request. The existing scheme, cookie and callback names remain compatible with established sessions. Mutations still require antiforgery; API 401 responses never redirect. Provider/admin secrets and Data Protection keys remain required for their existing purposes. There is no first-party signing-key requirement or fallback token path.

`RetireLocalPasswordVerifiers` removes the verifier column and legacy email index, while retaining old owner and expense rows. Its new constraint permits either a complete external identity or no external identity. Only existing legacy rows use the latter state. This is schema evolution: changing stored structure with explicit preservation rules rather than rebuilding the database. Keeping verifiers would retain unnecessary credential responsibility; deleting rows would destroy history; automatically matching email would give the wrong identity access. The cost is inaccessible historical rows until a separately authorized export/migration feature is designed.

## Cutover and fresh-account procedure

1. Stop application writes and the local stack with `aspire stop --non-interactive` from `PocketLedger.AppHost`. Preserve the AppHost UserSecretsId, both named volumes, provider/admin secrets and Data Protection key ring. Inventory the exact application/identity databases and owners before upgrade. Do not print or commit credentials.
2. Back up both databases with the appropriate PostgreSQL tooling and verify restoration into separate disposable databases before an important upgrade. A stopped-volume filesystem archive is an additional local fallback, only while all writers are stopped and with matching PostgreSQL major version; it is not a substitute for a tested database backup. Protect backups and key material as secrets, outside Git. Keep a copy of the pre-cutover revision and identity configuration.
3. Review the migration SQL: `dotnet ef migrations script 20261104195921_ExternalAccountsAndBrowserSessions --project src/PocketLedger.Infrastructure --output .artifacts/phase6-retirement.sql`. It drops the old email index/credential-kind constraint and `PasswordHash`, adds the paired-identity constraint and migration-history record, and performs no account/expense/ticket deletes or ownership updates. Verifiers are irreversibly removed. `Down` refuses rather than inventing password data.
4. In Development/Testing, startup applies the reviewed migration. Other environments must apply reviewed migrations separately; production Keycloak enablement remains outside this milestone. No old JWT secret is required. Normal startup never resets either volume or recreates provider users.
5. Existing external users sign in through their original realm and retain local account IDs/expenses. Former first-party users register fresh in Keycloak; even the same email creates an independent owner with no inherited expenses. Legacy owner/expense rows remain in place but cannot authenticate. This is a fresh-account boundary, not an account/password/expense migration or an archive/export product feature.
6. If a destructive reset is later wanted, obtain separate authorization naming the database, volume and affected account/expense/identity data after backup/export and restore review. No reset is required here and no deletion command is part of normal setup. Recreating a realm changes issuer/subject continuity; retaining the application volume alone cannot repair that relationship.

For local verification in this task, the stopped named volumes were archived to private ignored `.artifacts/phase6-backups/` before starting Aspire. These local fallback archives are sensitive and must not be published. A full restore rehearsal remains part of operational backup work, not evidence claimed by this task.

## Verification and learning exercise

The real-database upgrade test starts at `ExternalAccountsAndBrowserSessions`, inserts a legacy owner and an external owner with equal emails, owned purchases and a ticket, then applies retirement. It checks retained owners, amounts, identity continuity, exact ticket bytes/expiry, verifier-column absence and independent fresh provisioning. An attempted downgrade must fail explicitly while retaining migration history and owner rows. Expense HTTP tests now establish a test-host-only cookie session through the real local identity/ticket infrastructure and obtain real antiforgery tokens. This fixture does not prove provider login; the retained real-browser suite supplies that evidence without password grants or developer data.

1. Explain why removing `PasswordHash` does not require deleting its account row.
2. What could happen if a new provider user inherited a legacy account by email?
3. Follow an opaque provider subject through `ResolveExternalAccountHandler` to the cookie’s local account claim and an owner-filtered expense query.
4. Why must a verifier-removal downgrade refuse? Compare restoring a backup with fabricating a placeholder password hash.
5. Add a hypothetical export feature design that can serve historical owners without introducing automatic email linking. Identify the identity proof and authorization decision it would require.
